## Convergent root causes

Both passes independently identified the same core disease from different angles:

### DD and FCA are tool-layer integrations, not daemon-layer integrations

The architecture pass found this as candidates 3 and 4 (DD engine per-review, FCA rebuild per-review). The code review found it as findings `conventions-not-persisted` (high) and `dd-engine-per-review-cold-start` (medium). Both reach the same conclusion: the PRD describes these as maintained, incremental, daemon-resident state — but the implementation creates and destroys them on every `sutra_review` call.

The infrastructure for the PRD-specified design already exists:
- DD has `update()` and `evict_if_idle()` methods (untested in production)
- FCA has `update_incremental()` (tested but unused in production)
- SQLite has the `conventions` table with temporal columns (populated but never read)
- Config has `dd_idle_timeout_sec` (dead — hardcoded 60s in review.rs)

This is the single highest-leverage fix. Wiring DD and FCA into the daemon lifecycle resolves both passes' top findings, enables the PRD's temporal tracking story, and amortizes computation across multiple review calls.

### Stale spike entries distort all analysis

Architecture notes stale index entries are "harmless." Code review disagrees — finding `stale-spike-entries-in-index` shows they inflate dead code counts (70 of 103 dead symbols), distort file health reports, and confuse the code-intel summary. A single `sutra_parse` clears them, but the daemon should also prune deleted files proactively.

### Risk scoring concept spread

Architecture candidate 2 identifies duplicated risk-scoring logic between `pr_risk.rs` and `review.rs` — divergent weights, separate ChurnMap types, shared magic-number thresholds with no common definition. The code review notes the review compositor's weights are "sensible starting points" but doesn't flag the duplication. This matters because v1.1 HRR integration will need to tune these weights, and having two divergent copies guarantees drift.

## Recommendation

Ship v1 after Wave A (1-2 days of work). Wave B should follow immediately — the DD/FCA daemon integration is the single most impactful improvement and unblocks the PRD's temporal tracking story. Wave C is standard post-release cleanup.

The codebase is well-tested (311 passing tests, 0 failures), the module boundaries are sound, dependency direction is clean, and no correctness bugs were found. The main gap is between the PRD's vision of maintained/incremental state and the current per-call implementation — which works correctly today but doesn't deliver the full design.
