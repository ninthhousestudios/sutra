## Design

The architecture makes good decisions for this stage of the product. SQLite as the single source of truth, with DD and FCA as in-memory derived state rebuilt from it, is the right trade-off: it keeps persistence simple, avoids cache invalidation bugs between two storage layers, and means the daemon can crash without corrupting anything. The three-loop daemon design (scheduler, smriti watcher, MCP server) with per-workspace `tokio::Mutex` guards is clean and prevents the class of bugs where concurrent parses against the same DB would corrupt the index.

The review compositor (`src/tools/review.rs`) is the centerpiece of v1 and it is structurally sound. It composes DD constraint checking, FCA convention violation detection, churn analysis, and risk scoring into a single bounded response. The weight constants (W_BLAST=0.30, W_COMPLEXITY=0.20, W_HOTSPOT=0.15, W_CHURN=0.15, W_CONVENTIONS=0.20) are sensible starting points and exposed as named constants for tuning. Truncation (MAX_AFFECTED=20, MAX_READS=10) with total counts and truncation flags handles the context-window concern from the PRD.

The main design tension is between the PRD's vision and the current implementation. The PRD specifies conventions persisted in SQLite with temporal tracking (first_seen, last_seen), incremental extraction on each parse, and survival across daemon restarts. The implementation has the schema and DB methods for this but doesn't wire them up -- conventions are computed fresh in-memory on each `sutra_review` call and discarded. This is functional but means agents can't yet see "this convention is new" or "this convention disappeared," which is story 13 from the PRD. The infrastructure is in place; the integration is the gap.

## Findings

```yaml
- id: conventions-not-persisted
  severity: high
  category: design
  title: FCA conventions computed in-memory but never persisted to SQLite
  location: src/tools/review.rs:171-195
  evidence: |
    review.rs:build_findings() creates FcaEngine::new(), calls rebuild() and check(),
    but never calls db.upsert_convention(). The DB module has upsert_convention(),
    all_conventions(), delete_stale_conventions() -- none are called anywhere in the codebase.
    The conventions migration (0005_conventions.sql) creates the table, which sits empty.
  why: |
    PRD story 13: "conventions extracted incrementally on each parse and persisted in SQLite,
    so that I can see 'this convention is new' or 'this convention disappeared' over time."
    Without persistence: (a) every review call pays the full FCA rebuild cost, (b) agents
    cannot track convention evolution, (c) the first_seen/last_seen temporal columns have
    no data.  This is the single largest gap between the PRD and the implementation.
  recommendation: |
    After FcaEngine::rebuild() in build_findings(), iterate conventions and call
    db.upsert_convention() for each. Call db.delete_stale_conventions() with the
    current ID set. Optionally also run FCA rebuild in the parse pipeline
    (post_parse_sequence) so conventions update incrementally with each parse,
    not just on review.
  confidence: high

- id: dd-engine-per-review-cold-start
  severity: medium
  category: performance
  title: DD engine created and destroyed on every sutra_review call
  location: src/tools/review.rs:119
  evidence: |
    let engine = DdEngine::new(Duration::from_secs(60));
    engine.ingest(DdFacts { import_edges: edges })?;
    // ... query ...
    // engine dropped at end of build_findings()
    
    Each call spawns a timely worker thread, ingests all import edges, computes
    the full transitive closure, queries cycles + forbidden deps, then tears down
    the DD worker.
  why: |
    The PRD specifies DD as "lazy-populated on first DD-backed query and evicted
    after idle timeout" (story 19), with sub-second cold start (story 20). The
    current approach rebuilds the full TC on every review call. For a workspace
    with hundreds of files this is likely fine (sub-second), but it defeats the
    DD maintained-view design: the engine can't amortize work across multiple
    review calls or provide "your change introduces a new cycle" feedback that
    compares against a warm baseline.
  recommendation: |
    Hold a DdEngine instance per workspace in the daemon (alongside the Db).
    Ingest on first DD query, update on incremental parse, evict after
    dd_idle_timeout_sec (config already has the field). The review compositor
    should borrow the shared engine rather than creating a private one.
  confidence: high

- id: fca-approximate-implications-quadratic
  severity: medium
  category: performance
  title: FCA approximate_implications is O(n^2) in attribute count
  location: src/fca/context.rs:118-157
  evidence: |
    for a in 0..self.n_attrs {
        ...
        for b in 0..self.n_attrs {
            ...
            let both = self.attr_objects[a].intersect(&self.attr_objects[b]);
    
    This is a nested loop over all attribute pairs. With the current attribute
    schema (~15-20 attributes per symbol), n_attrs is bounded and this is fast.
    But attribute count grows linearly with: (a) new language grammars, (b) new
    attribute extractors in attributes.rs, (c) the "in:dir" path-based attributes
    which scale with directory depth.
  why: |
    At n_attrs=50, this is 2500 iterations with BitSet intersections.  At n_attrs=200
    (plausible with many languages and deep directory structures), it's 40,000.
    Each iteration does a BitSet intersection proportional to object count. This
    won't bite today but is the performance cliff for FCA scaling.
  recommendation: |
    Add a MAX_ATTRS cap (e.g., 100) that drops low-frequency attributes before
    building the formal context. The "in:" path attributes are the main growth
    vector and also the lowest signal -- they're the first to prune.  Alternatively,
    pre-filter to only attributes with support >= MIN_SUPPORT before the nested loop.
  confidence: medium

- id: review-freshness-envelope-missing
  severity: medium
  category: contract
  title: sutra_review response lacks per-entry freshness envelope
  location: src/tools/review.rs:65-99
  evidence: |
    The review handle() function returns a json!({...}) result that gets
    freshness fields merged by wrap_response() in mcp.rs. But there is no
    per-file or per-symbol freshness check. The PRD (story 22) requires:
    "every tool response to include a freshness envelope (fresh | edited_uncommitted
    | stale_index) per result entry."
    
    Other tools like sutra_map and sutra_find include per-result _freshness via
    freshness::check_file(). sutra_review does not.
  why: |
    An agent reviewing a diff needs to know which individual results to trust.
    If a changed file was edited after the last parse, the symbols and their
    complexity scores are stale for that specific file. Without per-entry
    freshness, the agent either trusts everything or trusts nothing.
  recommendation: |
    In gather_change_stats(), call freshness::check_file() for each changed path
    and include the result in the per-file and per-symbol JSON entries. FreshnessCounts
    already has the infrastructure.
  confidence: high

- id: dd-blast-count-retraction-logic
  severity: medium
  category: correctness
  title: DD blast_counts retraction uses fragile equality check
  location: src/dd/worker.rs:125-134
  evidence: |
    .inspect(move |((dst, count), _time, diff)| {
        let mut map = blast_counts_inspect.borrow_mut();
        if *diff > 0 {
            map.insert(*dst, *count);
        } else if *diff < 0 {
            if map.get(dst) == Some(count) {
                map.remove(dst);
            }
        }
    })
    
    The retraction path only removes the entry if the stored count matches
    exactly. In DD, a retraction is followed by a new insertion at the updated
    count. But the inspect callback sees retractions and insertions as separate
    events -- the retraction arrives with the OLD count, which should match.
    
    However, if two retractions arrive for the same dst before the insertion
    (possible during multi-step convergence), the second retraction sees a
    map that already had the entry removed. That's benign. The real risk is if
    a retraction arrives AFTER a new insertion has updated the count -- then
    the equality check correctly prevents erasing the new value. This is
    actually correct behavior for DD's consolidation model.
  why: |
    The logic works because DD consolidates before inspect sees the data (after
    step_while). But it's brittle: it relies on DD's consolidation guarantees
    that retractions and insertions for the same key are always seen together.
    If DD ever delivers partial updates (e.g., under backpressure), the map
    could become inconsistent. The cycle_nodes handling (HashSet insert/remove)
    is simpler and more robust.
  recommendation: |
    Consider matching the cycle_nodes pattern: maintain a HashMap<i64, isize>
    accumulator, and derive the final count from the accumulated value rather
    than relying on exact-match retraction. Or, since the TC is recomputed
    from scratch on each query anyway (after step_while), just snapshot the
    DD collection directly rather than maintaining a side-table.
  confidence: medium

- id: stale-spike-entries-in-index
  severity: low
  category: slop
  title: Removed spike binaries persist as stale entries in the sutra index
  location: project-wide
  evidence: |
    sutra_map returns entries for src/bin/fca-spike.rs, src/bin/hdc-spike.rs,
    src/bin/hrr-spike.rs, src/bin/salsa-spike.rs, src/bin/hdc-algebra.rs,
    src/bin/hdc-eval.rs, src/bin/hrr-semantic.rs, src/bin/dd-spike.rs.
    
    These files were removed from the filesystem (src/bin/ only contains guard.rs)
    and from Cargo.toml (no [[bin]] entries for them), but the sutra index still
    has them. The stale threshold mechanism doesn't prune deleted files; only an
    incremental parse with explicit delete events (via smriti watcher) removes them.
  why: |
    These ghost entries inflate symbol counts, distort health reports, and confuse
    dead code analysis (code-intel summary attributes ~70 of 103 dead symbols to
    spike binaries that no longer exist). They also distort the file map since
    hdc.rs and hrr.rs show as high-importance files.
  recommendation: |
    Run sutra_parse to trigger a full reparse, which will detect the missing files
    and cascade-delete them. For robustness, consider adding a "prune deleted files"
    step to parse_workspace that checks each indexed file's existence before the
    walk-and-parse loop.
  confidence: high

- id: review-diff-mode-hardcoded-main
  severity: low
  category: contract
  title: sutra_review branch mode hardcodes "main" as merge-base target
  location: src/tools/review.rs:76
  evidence: |
    _ => {
        let base = git::git_merge_base(workspace_root, "main")?;
        git::git_diff_files(workspace_root, &base, "HEAD")?
    }
    
    The default branch diff always uses "main" as the merge-base target.
    Projects that use "master", "develop", or other default branches will
    get a git error.
  why: |

    git_merge_base will fail with "fatal: Not a valid object name" if the

  recommendation: |
```

## Synthesis

The codebase is in good shape for a v1 release. The core structural analysis (parse, resolve, rollups, PageRank, impact) is mature with 311 passing tests and solid coverage of edge cases. The v1 additions (DD, FCA, review compositor, diagnostics, help) are architecturally sound and well-tested in isolation.

The two highest-priority follow-ups form a single root cause: **the v1 features are integrated at the tool layer but not at the daemon lifecycle layer**. Conventions are computed fresh per review call instead of persisting through the DB (finding: conventions-not-persisted). The DD engine is created and destroyed per call instead of living as a maintained view in the daemon (finding: dd-engine-per-review-cold-start). Both features work correctly today but don't deliver the "maintained" and "incremental" properties the PRD describes. These are the same integration that's needed: wire the FCA engine and DD engine into the daemon's per-workspace state, update them during incremental parse, and let the review compositor borrow rather than own them.

**Fix order:**
1. **conventions-not-persisted** -- highest impact, lowest effort. Just add upsert calls after rebuild(). This unlocks temporal tracking immediately.
2. **review-diff-mode-hardcoded-main** -- quick fix, prevents user-facing failures.
3. **review-freshness-envelope-missing** -- contract compliance, moderate effort.
4. **dd-engine-per-review-cold-start** -- larger refactor, but needed for the "maintained view" promise. Can ship without it.
5. **fca-approximate-implications-quadratic** -- future-proofing, not urgent today.
6. **dd-blast-count-retraction-logic** -- correctness hardening, not a current bug.
7. **stale-spike-entries-in-index** -- cleanup, one reparse fixes it.

The format drift (17 clippy warnings, ~45 files with fmt differences) should be cleaned up before release to avoid noise in subsequent diffs.

## Slop list

1. `src/fca/context.rs:150` -- `partial_cmp().unwrap()` on f64 confidence values. Safe today (confidence is always 0.0-1.0, never NaN) but fragile. Use `unwrap_or(std::cmp::Ordering::Equal)` instead. Also occurs in `src/tools/review.rs:326`.
2. `src/db.rs:1155-1224` -- `upsert_convention()`, `all_conventions()`, `suppress_convention()`, `delete_stale_conventions()` are all dead code (never called). Either wire them up (see finding conventions-not-persisted) or remove them to avoid confusion.
3. `src/fca/engine.rs:87` -- `let _ = attr_names;` is an explicit suppress of an unused variable. The attr_names are built but not returned from rebuild(). If they're not needed outside build_context(), don't return them.
4. `src/tools/review.rs:293-297` -- `sort_by` then `dedup_by` on different keys is a correctness smell. `dedup_by` only removes consecutive duplicates, so if two entries with the same name have different blast_radius values, they might not be adjacent after sort-by-blast. In practice each file path is unique per query result, but this should use a HashSet or sort-by-name-then-dedup instead.
5. `src/dd/worker.rs:29` -- `#[allow(dead_code)]` on `Response::Error`. This variant is never constructed by `run_worker` (only matched in engine.rs). Either the worker should send `Response::Error` on failure (instead of silently dropping via `let _ = resp_tx.send()`), or the variant should be removed and engine.rs should treat unexpected responses as errors directly.
6. `Cargo.toml:14-15` -- `sutra-guard` binary is declared but `src/bin/guard.rs` doesn't have corresponding spike binary entries for the removed files. Clean, but the version in Cargo.toml is 0.2.1 while README and MCP server report "v0.1.0". Pick one.
7. `src/tools/help.rs` -- The "conventions" topic describes FCA as detecting "naming conventions" and building a "concept lattice" for naming patterns. This overstates what the current implementation does. FCA extracts attribute implications (e.g., "pub functions tend to have docs"), not naming patterns. The help text should describe what FCA actually detects to avoid agent confusion.
8. `src/config.rs:43` -- `dd_idle_timeout_sec` is configured but never used (the DD engine is created per-call with a hardcoded 60s timeout in review.rs). Dead config.
