## what to pick up

### the immediate fork in the road

Decide whether to ship sutra v0.1 as a **standalone qartez replacement** (does not depend on smriti) or to **wait for smriti** and ship them together. Josh's verbal call this session was "standalone is good also" — read as a tilt toward standalone but not a firm commitment. Worth a 15-minute decision pass before writing any code:

- Standalone: faster path off qartez, sutra falls back to on-demand parse, easy to add smriti subscription later.
- Bundled: smriti's file-event stream is in flux; designing sutra around an unfinished subscription API risks rework.

### v0.1 implementation — when started

Design is concrete enough to begin. Suggested order:

1. Workspace registry + config (`~/.sutra/workspaces.toml`, `src/workspace.rs`).
2. Tree-sitter Rust parser + symbol/ref extraction (`src/parser/rust.rs`). Get `sutra_outline` working end-to-end on the sutra repo itself before adding Dart.
3. SQLite schema + indexer pipeline (`migrations/0001_initial.sql`, `src/db.rs`).
4. Core MCP tools first: `sutra_health`, `sutra_map`, `sutra_outline`, `sutra_find`, `sutra_read`. Then resolver-dependent tools (`sutra_refs`, `sutra_impact`).
5. Compute and store the load-bearing rollups (`files.fan_in_files`, `files.blast_radius`) on parse — these are needed for `sutra_impact` and seed the v0.1.5 guard calibration.

### v0.1.5 — modification guard

Do **not** start until v0.1 has been used against ≥5 real workspaces and you have a histogram of `fan_in_files` and `blast_radius` distributions. Calibrate thresholds at the 95th-99th percentile, not from qartez's defaults. Then ship:

- `sutra-guard` binary (PreToolUse hook).
- `sutra guard install` / `sutra guard uninstall` CLI.
- Filesystem-based ack protocol (`~/.sutra/acks/<workspace>/<blake3-of-relpath>`, 10-min TTL).

### v0.2 — pagerank

File-level (over imports) and symbol-level (over call/ref edges). Standard iterative algorithm, ~70 lines. Schema columns are already nullable in v0.1, so the addition is a population pass plus an extension to the guard's hot signal — no migration.

## context the next session needs

- Sutra is the bespoke replacement for qartez (kuberstar/qartez-mcp). Reasons: licensing (dual-licensed, not freely composable with the rest of manas) and surface area (39 tools, agent uses ~6). Sutra ships 12 tools across 2 tiers.
- Sutra is the **perception:code** subsystem of manas. Naming family: chitta (memory), smriti (filesystem), sutra (code), vedakosha (documents).
- Per-workspace, not home-wide. Smriti owns home-wide filesystem perception; sutra is scoped to explicit workspace roots.
- Stateless current-state index. Smriti owns file lifecycle; git owns commit history; sutra answers "what does the code mean now" and joins the others on demand.
- Tree-sitter only in v0.1 (Rust + Dart). No LSP. Honest cost: no macro/codegen expansion, no real type-system disambiguation.
- No vector/embedding index in v0.1. Embeddings are v0.3 *maybe*, never primary. Keeps the "structure over text" promise sharp.
- Daemon over Unix socket, fronted by mcpjungle. Same shape as smriti.

## blockers / dependencies

- **Smriti file-event subscription API.** Sutra v0.1 can ship without it (on-demand parse fallback), but the subscription is the right long-term integration. Coordinate with smriti's open question on downstream consumer subscription.
- **mcpjungle.** Sutra assumes the same socket/proxy story as chitta and smriti. No new requirements on mcpjungle, but the assumption should be sanity-checked before standing up the daemon.
